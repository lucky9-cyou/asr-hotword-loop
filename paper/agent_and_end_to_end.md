# ECHO 的 Agent 与端到端研究计划

状态：研究设想。当前 Demo 实现的是 ASR → LLM 提取 → 词库累加 → 后续解码偏置，尚未实现下列完整 action agent 或端到端训练。

## 从提取器扩展为动作决策

同一个 agent 每轮可以输出零个或多个动作：

| 动作 | 作用 | 例子 |
|---|---|---|
| `hotword.add` | 新增有解释依据的实体 | 学到“余明洞” |
| `hotword.update` | 修正已有实体的写法或偏置配置 | 将“鱼明洞”替换为“余明洞”，避免两者同时残留 |
| `hotword.delete` | 删除错误、过期或被要求忘记的条目 | 不再偏向已被否定的名字 |
| `history.correct` | 根据后来解释修订历史转写 | 把前一轮的“鱼明洞”在修订视图中改成“余明洞” |
| `noop` | 不做修改 | 普通闲聊、证据不足或没有新信息 |

动作应包含目标实体/轮次、变更前后内容、原文证据与简短理由。更新和删除需要稳定实体 ID，不能仅追加另一种拼写。历史转写保留原始 ASR 输出及独立修订版本，不覆盖原始记录；每项变更可追踪和撤销。默认作用域为当前会话。

## 端到端方向

未来输入为当前音频、历史会话和当前词库，模型在一次推理中联合完成：

```text
音频 + 历史 + 词库
  → 结构化 thinking：恢复解释词 → 确定实体用字 → 选择动作
  → 当前转写 + 记忆动作 + 可选历史修订
```

将现阶段“LLM 生成热词”的功能纳入模型的可监督中间过程，而不是永久依赖外接提取器。thinking 可采用简短、可核查的字段，如解释来源、目标字和动作；长自由文本推理不是必要条件。动作由执行层校验、应用，音频识别与词库状态的先后顺序需明确，防止使用未来轮次的信息。

可比较：现有级联系统、级联 action agent、带结构化 thinking 的端到端模型，以及不输出 thinking 的端到端消融。训练数据可包含转写、解释锚点和动作轨迹，损失设计、模型结构和训练结果待研究。不能把生成了推理文本本身当作推理正确的证据。

## 与 Benchmark 的关系

[ECHO-Bench 协议](../benchmarks/echo_bench/README.md)将分别衡量当前识别、未来实体识别、记忆动作和历史修订。需要检查错误记忆传播、无关实体插入、过度纠正和删除后的残留影响。正式数据集和训练尚未开展。
